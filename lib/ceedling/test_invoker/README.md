# The Test Build Pipeline

The test pipeline turns a list of test-file paths into compiled, linked, executed test results by carrying one independent record per test file through a fixed, ordered sequence of stages, each of which reads what earlier stages have already figured out and fills in a little more.

Every test file in a run gets its own `Testable` record, and every `Testable` in the run travels together inside one `PipelineState`. A stage never looks at a test file directly except through its `Testable`; it never looks at the whole run except through `PipelineState`. Early stages are about *finding out*: what does this test file `#include`, what build directives does it carry, what mocks and Partials does it need. Later stages are about *doing*: preprocessing, generating mocks and Partials, compiling, linking, and finally running the test executable and collecting its results. Nothing is skipped by accident -- every stage in the sequence still gets visited on every run, but most stages carry a condition that lets them recognize a run where they have nothing to do and quietly step aside.

## The pipeline's shape

Five classes divide the work, and each owns a different concern:

- **`TestInvoker`** owns one test-build *run*, top to bottom. It opens the dependency cache before the run and flushes it afterward, fires the `pre_test_build`/`post_test_build` plugin hooks around it, and if anything anywhere in the pipeline raises, it's the one that catches the exception, logs it, and registers the run as a failed build rather than letting the exception escape. It also answers a couple of narrow questions once a run has finished -- which sources a given test pulled in, mainly for callers outside the pipeline that only care about dependency information and never asked for a real build.
- **`TestPipelineManager`** owns the *stage sequence* itself: the fixed list of stages in the order below, and the handful of feature-toggle and stop-point conditions that let a stage recognize it has nothing to do on a given run. It has no idea how any stage actually accomplishes its work -- it only decides whether a given stage runs at all.
- **`TestBuildSetup`** does the early, per-test *groundwork*: creating build directories, extracting a test file's `#include`s and build directives, and working out the flags, defines, and search paths every later stage will need.
- **`TestBuildPlanner`** decides *what* needs to be generated and built -- which mocks a test needs, what its generated runner and Partials will look like, and, once everything upstream has run, the final list of sources, objects, and artifacts that have to be compiled and linked.
- **`PartialsManager`** preprocesses each Partial's header and source files and generates its actual implementation, interface, and (when needed) types-header content, calling into `Partializer` (`lib/ceedling/partials/`) for the underlying C-parsing/extraction work.
- **`TestBuildExecutor`** does the rest of the actual *work* the planner decided on: generating mocks, compiling objects, linking executables, and running the resulting test fixtures.

`TestBuildSetup`, `TestBuildPlanner`, `PartialsManager`, and `TestBuildExecutor` never call each other directly -- `TestPipelineManager` is the only thing that sequences them, and it does so purely by calling each stage's method against the shared `PipelineState` in turn.

## `PipelineState` and `Testable`

`PipelineState` is the one object that exists for the whole run; a `Testable` exists once per test file. Between them they hold everything a stage might need to read or write, grouped loosely by what it's for:

- **Identity**: a `Testable`'s `filepath` and `name` -- set once, in the first stage, and never changed again.
- **Paths and preprocessing scratch state**: where this test's build output, mocks, Partials, and preprocessed files live, and the bookkeeping preprocessing needs along the way. These stay as plain Hashes rather than dedicated structs because their keys are sparse and conditional -- a project with mocking disabled simply never has a `:mocks` path at all, which a Hash tolerates far more gracefully than a struct field with no meaningful default.
- **Flags, defines, and search paths**: the compiler/linker/preprocessor arguments resolved once per test, reused by every later stage that invokes a tool.
- **Generated-content records**: `runner` (a `RunnerInfo`), each resolved mock in `mocks` (a `MockDetails`), and `partials` (a `TestablePartials`, itself holding a config map plus the two lists of module names Partials generation has actually produced so far). Unlike the sparse path/preprocessing Hashes, these have a fixed, known shape every instance shares, which is exactly what a struct is for -- a typo'd field name fails loudly instead of silently doing nothing.
- **Build artifacts and results**: the final sources, objects, and executable path a test resolves to, and where its pass/fail results get written.
- **`executable_rebuilt`**: a boolean carried on the `Testable` rather than re-derived later, because by the time anything downstream would want to ask "was this just rebuilt?", the dependency tracker has already been told the executable is fresh -- asking it again would always answer "no," regardless of what actually happened moments before.

`PipelineState` itself carries the overall list of tests, the accumulated `Hash` of every `Testable` in the run, the run's context and control options, a `Mutex` guarding concurrent writes into that Hash, and four accumulator lists -- `partials_headers`, `partials_sources`, `mocks_list`, and `objects_list` -- that exist purely so later stages can hand every partial file, mock, or object across every test to the parallelism machinery as one flat batch instead of one nested loop per test. Each item in those lists (`PartialWork`, `MockWork`, `ObjectWork`) is itself a small struct rather than an ad-hoc Hash, for the same reason `RunnerInfo` and `MockDetails` are: their shape is fixed and known in advance, so it deserves a name.

## The stages, in order

**Context collection (stages 1-4)** figure out what a test file actually needs, without generating or compiling anything yet. Stage 1 creates each test's build directories and gives it its `Testable` record. Stage 2 scans the test file for its `#include`s, build-directive macros, and test case names. Stage 3 resolves the flags, defines, and search paths every later tool invocation for this test will use. Stage 4, when real preprocessing is enabled, re-extracts the test file's includes through the actual preprocessor rather than a plain text scan, since macros can hide or introduce includes a text scan alone would miss.

**Planning (stage 5)** is where `TestBuildPlanner` decides what this test needs generated: which of its includes are mocks and where each one's real header actually resolves to, what its Partials configuration looks like, and where its generated test runner will live. Nothing is generated yet -- stage 5 only decides.

**Partials (stages 6-8)**, owned by `PartialsManager` and run only when a project uses Partials at all, and only when this particular run actually has any. A transform first flattens every test's Partials configuration into two flat lists -- one for partial header files, one for partial source files -- so stages 6 and 7 can preprocess every partial file across every test as a single parallel batch rather than nesting per-test loops. Stage 8 then extracts and generates each partial's actual implementation and interface content from whatever those preprocessing passes produced.

**Mocks (stages 9-10)**, run only when a project uses mocks at all, and only when this particular run actually has any. A transform flattens every test's planned mocks into one flat list the same way Partials' own transform does. Stage 9, when mock preprocessing is enabled, preprocesses each header to be mocked. Stage 10 generates the actual mock source and header CMock will compile in. This is also the pipeline's first stop point: a run that only wants mocks regenerated (a `--mocking-only`-style build) stops right after this stage.

**Test-file preprocessing (stages 11-13)** work on the test file itself rather than anything it includes. Stage 11 preprocesses the test file and extracts any `TEST_SOURCE_FILE()` build directives from the result. Stage 12 parses test case names out of that preprocessed output. Stage 13 generates the actual Unity test runner C file -- this pipeline's second stop point, for a run that wants runners regenerated without going all the way to a real compile.

**Artifact determination, build, and execution (stages 14-17)** close out the run. Stage 14 resolves the final, complete list of sources, objects, executable path, and results paths for every test -- everything upstream was preparation for this. A transform flattens every test's objects into one flat list, the same pattern Partials and mocks use, so stage 15 can compile every object across every test as a single parallel batch. Stage 16 links each test's executable. Stage 17 runs each resulting test fixture and collects its pass/fail results -- the pipeline's last two stop points sit right around here: one stops before stage 15 ever compiles anything, and one runs stages 15-16 but stops short of actually executing anything in stage 17.

A module a Partial has taken over is excluded from a test's *linked* objects, since the Partial's own generated source is what actually gets linked for that module -- but the original module's own source is still compiled at stage 15 like every other source in the test, and is only trimmed from the objects handed to the linker at stage 16, right before linking. Compiling it unconditionally keeps that source's own dependency tracking working the same way it does for every other source, regardless of whether the resulting object ever actually links; under coverage profiling (`gcov`, Bullseye) it also keeps the `#line` directives that map a Partial's generated code back to the original module's own lines accurate, since that mapping only holds if the original module is actually run through the coverage toolchain's compiler.

## Stop-point flags

A run can ask the pipeline to stop early by including one of four mutually exclusive Symbols in `PipelineState#options`: `:mocking` (stop after stage 10), `:test_runner` (stop after stage 13), `:sources_only` (skip stages 15-17, running only enough to populate each test's `.sources`), and `:build_only` (skip stage 17 only, so tests compile and link but never run). Supplying more than one of these at once is rejected outright, since each names a different, specific point to stop at and there's no sensible way to honor two at once. A fifth option, `:refresh_dependencies`, isn't a stop point at all -- nothing in the stage sequence looks at it; `TestInvoker` reads it directly to decide whether the dependency cache should prune entries for targets this run never touched.

The mechanism behind all of this is quieter than it might sound: every stage in the sequence is still visited on every single run, with no special "stop the pipeline" signal anywhere. Each stage simply carries its own condition -- a check against `PipelineState#options` -- and skips itself when that condition says there's nothing to do. A `:mocking` run doesn't short-circuit the loop after stage 10; stages 11 through 17 are still visited, they just each recognize `:mocking` is present and decline to run. This is also exactly how the ordinary feature toggles work -- a project with Partials disabled skips stages 6-8 by the same mechanism, with no stop point involved at all.

The three Partials stages and the two Mocks stages carry a second check on top of that feature toggle. A project can have Partials or mocking enabled overall while a particular run still has none of that kind of work -- a `test:pattern` run scoped down to files that use neither, for instance. When a stage's feature is enabled but this run's own work for it turns out empty, the stage still declines to run, exactly as it would if the feature were off, but it doesn't stay silent about it the way a disabled feature does. Each of these five stages logs one line at the OBNOXIOUS verbosity level, naming itself and noting there was nothing to do, so a run scoped down to a handful of files doesn't lose its ordinary output to a run of headings with nothing under them.

## Parallelism

Most stages hand their per-test or per-item work to `Batchinator`, which spins up a pool of worker threads sized from the project's configured thread count and runs the given block once per item concurrently. This is why so much of the pipeline's code is wrapped in a block passed to `@batchinator.exec` and guarded by `PipelineState#lock.synchronize` wherever it writes into the shared `testables` Hash or an accumulator list -- concurrent writes to ordinary Ruby collections aren't safe without that guard, and every stage that mutates shared state through this pipeline takes care to hold the lock only for the write itself, not for the real work (preprocessing, compiling, and so on) that produced it.
