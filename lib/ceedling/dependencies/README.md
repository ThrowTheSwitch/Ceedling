# The Dependency-Tracking Subsystem

This subsystem answers one question, for any expensive step in either the test or release pipeline: has anything this target depends on changed since it last built successfully -- using content hashes rather than timestamps, so neither pipeline ever redoes work that doesn't need redoing.

It is not itself a pipeline with sequential stages the way `test_invoker`/`release_invoker` are. It's a service both pipelines call into, over and over, as a pure oracle: it never decides *when* to run a build step or *what order* steps happen in -- that's Rake's task graph and each pipeline's own stage list -- it only answers, at the moment a step is about to run, whether it actually needs to.

## The subsystem's shape

Two classes matter most, and everything else exists to serve them:

- **`Dependinator`** is the thin, Ceedling-specific facade every pipeline actually talks to. Every method it has except one is a one-line passthrough to `DependencyTracker` below; what it actually owns is the convention for where a given pipeline's cache file lives on disk, keyed by a symbolic identifier (`:test`, `:release`, or a plugin's own symbol), and the vocabulary translation at `flush` time from the tracker's own `prune:` parameter to the pipeline-facing `refresh_dependencies:` (see below). Its whole reason for existing is so pipeline code speaks in build verbs -- register this, ask if that's stale, mark this fresh -- and never has to know anything about cache file paths or tracker internals.
- **`DependencyTracker`** is the actual engine, and it's deliberately generic and application-agnostic -- nothing in it knows what a "test" or a "release" is. It holds this run's registrations in memory and a loaded cache of the previous run's hashes, and its whole job is answering staleness queries against the two. It calls itself "a pure query module, not a build scheduler" for a reason: cascading rebuilds and ordering are Ceedling's existing task graph's job, not this class's.

`DependencyTracker` in turn composes four narrowly-scoped collaborators, each doing exactly one job and nothing else: `DependencyHasher` (what makes two things count as "the same"), `DependencyPathNormalizer` (what makes two spellings of a path count as "the same target"), `DependencyCacheStore` (the on-disk cache file itself), and `GccDependencyParser` (turning a compiler's own dependency output into something registerable). Each gets its own section below, the same way the sibling pipeline READMEs name `Batchinator`'s role without documenting its internals.

## The register → stale? → mark_fresh idiom

Every call site in both pipelines, regardless of what expensive thing it's guarding -- a preprocessor subprocess, a CMock generation, a real compiler or linker invocation -- follows the same three-part shape. `register` tells the tracker what a target depends on: its antecedent files, and a `meta` value carrying anything else that should count toward staleness even though it isn't a file at all -- compile flags, `-D` defines, search paths, a toolchain version string, a coverage-on-or-off flag. An object file's target is the `.o` itself; its files are its source plus (once the compiler has run at least once) whatever headers it actually pulled in; its meta is the flags and defines that, if they change, should force a recompile even though the source file itself didn't change a byte.

`register` is additive on purpose: calling it more than once for the same target unions the file lists and merges the meta rather than replacing what came before, so a target's dependencies can be built up incrementally across more than one call site without either caller needing full knowledge of what the other already supplied. This is exactly what lets a compile step register its source file and known flags in one call, and separately register whatever headers the *previous* compile's `-MMD -MF` output discovered, via `register_gcc_deps_file` -- which is really just "parse this `.d` file's Makefile-dialect content into however many targets and dependency lists it actually describes, and `register` each one," since a single `.d` file can describe more than one target at once, not "the dependency list for one file."

Once a target's inputs are registered, `stale?` is a pure question with no side effects, and `mark_fresh` is the write that happens after a real (re)build succeeds, recording new hashes for the target itself, its meta, and every currently-existing dependency. A dependency that's gone missing is simply left out of what gets recorded -- `stale?` already treats a missing dependency as stale on its own, so there's nothing to gain by recording anything else about it.

## What makes two things "the same"

Two decisions make this whole scheme trustworthy rather than merely convenient, and both trade a little efficiency for a lot of certainty.

`DependencyHasher` hashes a file's exact on-disk bytes, whitespace included, with no format-aware normalization at all -- and that's deliberate, not an oversight. Whitespace isn't reliably cosmetic (it's syntactically meaningful in YAML, and can even change whether a C macro's line continuation is recognized), and the two ways a hash-based staleness check can be wrong aren't equally bad: reporting something stale when it isn't just costs a wasted rebuild, but reporting it fresh when it isn't means shipping a build that silently doesn't reflect its own source -- exactly the failure this whole subsystem exists to prevent. The same hasher canonicalizes a `meta` value before hashing it, so that hash-key order and Symbol-vs-String keys never matter, while still preserving array element order, since the order of a flags or defines list can itself be meaningful.

`DependencyPathNormalizer` solves a narrower but equally important problem: resolving a path to its real, on-disk casing before it's ever used as a cache key, so that a `#include "Foo.h"` written one way and a file that actually exists on disk as `foo.h` -- or the same real file assembled from project configuration two different ways -- can never be mistaken for two different targets.

## The on-disk cache

Each pipeline identifier gets exactly one JSON cache file of its own, never shared with any other identifier -- test and release builds each get their own, and a plugin introducing a third pipeline would get a third, just by choosing its own identifier. This isn't incidental: it's what makes the pruning behavior described below safe at all, since a shared cache would mean a full test run's prune could silently evict every cached release entry along with it.

Loading that cache is deliberately forgiving in one direction and strict in another. Any structural surprise in the file as a whole -- it's missing, malformed, or was written by an incompatible version of this subsystem -- degrades the entire store to empty rather than raising, which just means a full rebuild rather than a hard failure. A single malformed *entry* within an otherwise-good file, similarly, only drops that one entry. And on every load, entries whose target has since been deleted from disk are pruned automatically and unconditionally -- this is always safe regardless of how complete or partial the run that created it was, since a target that's provably gone is gone no matter what, which is exactly what distinguishes it from the opt-in pruning described next. Persisting the cache back out is done via a write-to-temp-file-then-rename, so a reader can never observe a half-written cache.

## `refresh_dependencies`: the special feature

This is this subsystem's answer to the sibling READMEs' stop-point flags and single-file compile-check mode -- an opt-in behavior that changes what happens at the very end of a run, and one that's easy to get backwards if you don't know exactly when it's safe.

A normal `flush` just persists whatever this run registered and learned. Passing `refresh_dependencies: true` additionally drops every cache entry whose target was *not* registered at some point during this run, before persisting -- in effect, treating this run's registrations as the complete, authoritative set of everything that should still have a cache entry at all. That's exactly correct for a run that's guaranteed to have touched every target that matters -- a full `test:all`, or a full release build -- and exactly wrong for anything less than that: a single test file, `test:pattern`, `test:path`, or the ad hoc single-file `release:compile:`/`release:assemble:` tasks would each, if this were set true, silently wipe out cache entries for every target the partial run simply didn't happen to touch, forcing an unnecessary full rebuild on the next real run. Both pipelines are careful to set it only when they can actually make that guarantee -- and never otherwise.

## Debugging a stale/fresh surprise

Separately from anything either pipeline does on a normal run, this subsystem carries an opt-in troubleshooting aid for a human trying to understand *why* something did or didn't rebuild. Setting the `CEEDLING_DEP_DEBUG` environment variable turns on a tiered snapshot mechanism: a lighter tier captures just the canonicalized meta a target was judged against, and a fuller tier additionally captures the actual content of the target and its dependencies at the moment they were last marked fresh, into a human-readable file tree alongside the cache -- capped in size per file, so one enormous generated header can't silently balloon that tree.

Those snapshots exist to back one thing: an always-available "explain yourself" query that reports which of a target's self-hash, meta-hash, or dependency-hashes changed, and -- wherever a prior snapshot happens to be available -- an actual before/after diff rather than just a yes-or-no changed flag. This query works with no debug tier active at all; it just has less to show without a snapshot to compare against.

## Shared vocabulary with both pipelines

This isn't merely a similar pattern independently followed by two pipelines -- it's the literal same collaborator, called identically, from both. The register → stale? → mark_fresh idiom above is the connective tissue running through this README and the two pipeline READMEs alongside it: every one of those pipelines' stages/steps that does something expensive is, underneath, just another caller of this same three-part shape.

One relationship is worth calling out explicitly, because it's the one place this pattern is conspicuously absent rather than present: the preprocessor itself never holds a reference to this subsystem at all. Every pipeline that uses the preprocessor registers its own targets and checks their own staleness *before* ever invoking it, and the preprocessor does no freshness checking of its own. That's not an oversight -- it's the same underlying principle this whole subsystem is built on, pushed one level further: the thing doing expensive work should never be the thing deciding whether that work is needed. That decision belongs, every time, to whichever caller can see the whole picture.
